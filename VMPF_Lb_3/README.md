# Лабораторна робота №3

**Тема:** Створення мобільного застосунку за допомогою Kotlin (Android)
**Варіант:** тема 3 — **«Каталог товарів»** (та сама тема, що й у ЛР2)
**Обсяг:** Рівень 1 (відображення товарів) + Рівень 2 (кошик та оформлення замовлення) — **75 балів**

---

## Опис

Мобільний застосунок інтернет-магазину на **Kotlin + Jetpack Compose**. Це
клієнтська (мобільна) частина для тієї ж теми, що реалізована у ЛР2: застосунок
звертається до **того самого REST API сервера на Node.js + Express** із ЛР2.

Архітектура — **MVVM** (Model–View–ViewModel):

- **View** — екрани на Jetpack Compose (декларативний UI);
- **ViewModel** — стан екранів (`StateFlow`), бізнес-логіка, валідація;
- **Model / Data** — репозиторії, мережевий шар на Retrofit, сховище кошика.

### Реалізований функціонал

**Рівень 1 — Каталог товарів:**
- відображення списку товарів, отриманих із сервера (сітка карток);
- екран детального перегляду товару;
- фільтрація за категоріями, пошук за назвою, сортування за ціною/рейтингом
  (через query-параметри `?category=`, `?search=`, `?sort=`).

**Рівень 2 — Кошик та оформлення замовлення:**
- додавання товарів у кошик, зміна кількості, видалення;
- збереження кошика у `SharedPreferences` (не зникає після перезапуску — аналог
  `localStorage` вебверсії);
- екран оформлення замовлення з формою та валідацією (клієнт + сервер);
- відправка замовлення на сервер (POST), екран підтвердження з деталями замовлення.

## Технології

- **Kotlin** 1.9, **Jetpack Compose** (Material 3) — UI;
- **Navigation Compose** — навігація між екранами;
- **Retrofit 2 + Gson + OkHttp** — звернення до REST API;
- **Coroutines + StateFlow** — асинхронність і реактивний стан;
- **Coil** — завантаження зображень товарів;
- **ViewModel (AndroidX Lifecycle)** — керування станом екранів.

## Запуск

### 1. Запустити сервер ЛР2

Мобільний застосунок використовує REST API із ЛР2. Спочатку запустіть сервер:

```bash
cd <шлях-до-LR2>/VMPF_Lb_2/server
npm install
npm start          # сервер на http://localhost:3000
```

### 2. Відкрити мобільний проєкт

1. Відкрийте папку `VMPF_Lb_3` в **Android Studio** (File → Open).
2. Дочекайтесь синхронізації Gradle (Android Studio сам завантажить потрібний
   Gradle і залежності; SDK обирається автоматично, файл `local.properties`
   створюється IDE).
3. Запустіть на **емуляторі** (Run ▶).

### Адреса сервера

У файлі `RetrofitClient.kt` базова адреса:

```kotlin
const val BASE_URL = "http://10.0.2.2:3000/"
```

- `10.0.2.2` — спеціальна адреса, за якою **емулятор Android** бачить `localhost`
  комп'ютера. Сервер ЛР2 при цьому має бути запущений на хост-машині.
- Для запуску на **фізичному пристрої** замініть на IP комп'ютера в локальній
  мережі, напр. `http://192.168.0.10:3000/` (пристрій і ПК — в одній мережі).

Незашифрований HTTP до локальної адреси дозволено через
`res/xml/network_security_config.xml`.

## API (маршрути сервера ЛР2, які використовує застосунок)

| Метод | URL | Опис |
|-------|-----|------|
| GET | `/api/products` | Список товарів. Параметри: `?category=`, `?search=`, `?sort=price_asc\|price_desc\|rating` |
| GET | `/api/products/categories` | Список категорій |
| GET | `/api/products/:id` | Деталі товару |
| POST | `/api/orders` | Створення замовлення (валідація, 201 / 400) |
| GET | `/api/orders/:id` | Деталі замовлення |

## Відповіді на контрольні запитання

**1. Як організовано структуру проєкту?**
Single-activity застосунок із поділом за шарами (MVVM): `data` (моделі, мережа,
репозиторії), `ui` (екрани Compose + ViewModel, навігація, тема, компоненти).
Кожен екран — окремий пакет із парою «Screen + ViewModel».

**2. Які основні завдання виконує серверний застосунок?**
Сервер (із ЛР2) віддає список і деталі товарів, приймає та валідує замовлення,
рахує суму, зменшує залишки на складі. Мобільний застосунок — клієнт цього API.

**3. Як інтегровано бібліотеку для мережі?**
Через Retrofit: інтерфейс `ApiService` з анотаціями `@GET`/`@POST`, клієнт
налаштовано в `RetrofitClient` (base URL, OkHttp з логуванням, конвертер Gson).

**4. Які маршрути реалізовано?** Див. таблицю API вище.

**5. Як організовано взаємодію з даними?**
Через `ProductRepository`, що інкапсулює виклики Retrofit і повертає `Result<T>`.
Дані зберігаються на сервері (in-memory store ЛР2); локально зберігається лише кошик.

**6. Які моделі даних використано?**
`Product`, `Category`, `Order`, `OrderItem`, `Customer`, `OrderRequest`, `CartItem`
(див. `data/model/Models.kt` та `CartRepository.kt`).

**7. Як забезпечено обробку помилок?**
`runCatching` у репозиторії + `parseApiError`, що розбирає тіло помилки сервера
(`{ error }` / `{ errors: [] }`) та повідомлення про відсутність з'єднання. На екранах —
стани `LoadingState` / `ErrorState` з кнопкою «Повторити».

**8. Аутентифікація та авторизація?**
У межах Рівнів 1–2 не вимагається (це Рівень 3). Архітектура дозволяє додати
перехоплювач OkHttp із токеном без зміни наявних екранів.

**9. Як використано стан (state)?**
Кожен ViewModel тримає незмінний `data class …UiState` у `MutableStateFlow`;
екран підписується через `collectAsState()`. Глобальний стан кошика — `CartRepository`
зі своїм `StateFlow`.

**10. Як організовано реактивне оновлення інтерфейсу?**
Compose автоматично перемальовує composable при зміні стану, на який він підписаний.
Лічильник кошика в шапці оновлюється миттєво, бо читає `CartRepository.items`.

**11. Як інтегровано клієнт із сервером?**
Через HTTP-запити Retrofit до `http://10.0.2.2:3000/` (емулятор → localhost ПК).

**12. Які UI-компоненти використано?**
`Scaffold`, `TopAppBar`, `LazyVerticalGrid`, `LazyColumn`, `Card`, `FilterChip`,
`OutlinedTextField`, `Button`, `BadgedBox`, `DropdownMenu`, `AsyncImage` (Coil) тощо.

**13. Як реалізовано навігацію?**
Navigation Compose: `NavHost` з маршрутами `catalog`, `product/{id}`, `cart`,
`checkout`, `order/{id}` (аналог конфігурації React Router у ЛР2).

**14. Як організовано управління формами?**
Контрольовані поля: значення у стані ViewModel, оновлення через `onValueChange`,
відправка через `submit()` після валідації.

**15. Як реалізовано валідацію даних?**
На двох рівнях: клієнтська у `CheckoutViewModel.validate()` (ім'я, email-regex, адреса)
та повторна серверна (сервер ЛР2 повертає 400 із переліком помилок).

**16. Як забезпечено створення/редагування/видалення ресурсів?**
Створення — POST замовлення. Редагування/видалення позицій кошика — методи
`add` / `setQuantity` / `remove` / `clear` у `CartRepository` з негайним
відображенням завдяки `StateFlow`.

**17. Оптимізація завантаження?**
Ліниві списки (`LazyVerticalGrid`/`LazyColumn`) рендерять лише видимі елементи;
зображення кешуються Coil; пошук виконується з debounce (затримка 400 мс).

**18. Інтеграція зовнішніх сервісів?**
Зображення товарів — зовнішній сервіс `picsum.photos` (URL приходять із сервера).

**19. Як тестувався застосунок?**
Перевірено сценарії: завантаження каталогу, фільтр/пошук/сортування, перегляд
товару, додавання в кошик, зміна кількості, оформлення з валідним і невалідним
введенням, підтвердження замовлення; перевірено стани помилки при вимкненому сервері.

**20. Основні виклики?**
Доступ емулятора до локального сервера (`10.0.2.2` + cleartext-конфіг),
коректна валідація на двох рівнях, збереження кошика між запусками
(`SharedPreferences`), реактивне оновлення лічильника кошика на всіх екранах.
